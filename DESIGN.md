# Project Watchtower - Architecture & Design Document

## 1. Data Structures: EventEnvelope

All data generated by the four mock sources (**Dynatrace**, **Splunk**, **Riverbed**, and **Prometheus**) is wrapped in a standardized `EventEnvelope` structure before being sent to the ingestion channel. This ensures a consistent processing pipeline across all data sources.

```go
type EventEnvelope struct {
    Version   string                 `json:"version"`   // Required version field
    ID        string                 `json:"id"`        // Unique identifier (UUID)
    Source    string                 `json:"source"`    // "dynatrace", "splunk", "riverbed", "prometheus"
    Timestamp int64                  `json:"timestamp"` // Unix timestamp
    Payload   map[string]interface{} `json:"payload"`   // Flexible payload varying by source
}
```

## 2. Object Storage Key Schema

Since the use of a database is not permitted, all application state and data will be stored in MinIO (S3-compatible) using the following key structure.

### Raw Events

```text
/events/raw/YYYY/MM/DD/HH/<uuid>.json
```

### Screened Events

```text
/events/screened/YYYY/MM/DD/HH/<uuid>.json
```

### Anomaly Outputs

```text
/ml/anomalies/YYYY/MM/DD/<uuid>.json
```

### Forecasts

```text
/ml/forecasts/YYYY/MM/DD/<metric>.json
```

Forecast files are overwritten whenever a new prediction becomes available.

### Active Policy

```text
/policy/screening.json
```

### Dashboard Snapshot

```text
/state/dashboard.json
```

### Deduplication TTL Buckets

```text
/dedup/window/<bucket>.json
```

## 3. Channel Buffer Strategy & Backpressure

The system uses a single centralized buffered channel:

```go
chan EventEnvelope
```

### Buffer Size

The channel capacity is not hardcoded. Instead, it is injected dynamically through:

```json
ingestion.channel_buffer_size
```

defined in `config.json`.

### Backpressure Handling

To prevent application crashes during high load or burst traffic scenarios, mock producers use a `select` statement with a `default` case:

```go
select {
case ingestionChan <- event:
    // sent
default:
    // drop event
}
```

If the channel is full, the event enters the `default` branch and is discarded.

### Monitoring

Every dropped event must:

* Be recorded in the application logs.
* Increment the drop counter metric.
* Be exposed through the dashboard for monitoring purposes.

## 4. Goroutine Ownership Map

To prevent data races and maintain clear responsibility boundaries, goroutines are organized as follows.

### Producers (4 Goroutines)

One independent goroutine for each source:

* Dynatrace
* Splunk
* Riverbed
* Prometheus

#### Responsibilities

* Generate mock data.
* Act as the sole writers to the ingestion channel.

### Consumers / Worker Pool (N Goroutines)

The number of workers is defined by:

```json
screening.worker_count
```

in `config.json`.

#### Responsibilities

Read events from the ingestion channel and execute the screening pipeline:

1. Deduplication
2. Classification
3. Noise Filtering

### Background Policy Poller (1 Goroutine)

A dedicated goroutine periodically polls:

```text
/policy/screening.json
```

using ETag support to perform hot-reloading of screening rules without blocking the main processing pipeline.

### Storage Archiver (1 Goroutine)

Listens to a secondary channel from the ingestor and asynchronously writes raw events to MinIO.

#### Purpose

Prevent storage latency from impacting ingestion throughput.

## 5. Graceful Shutdown Sequence

The application must support a clean shutdown and exit within a maximum of **5 seconds** after receiving an interrupt signal.

### 1. Signal Capture

Listen for the following signals using the `os/signal` package:

* SIGINT
* SIGTERM

### 2. Context Cancellation

Invoke the global `context.CancelFunc` to notify all producers to stop generating mock data.

### 3. Channel Closure

After all producers have confirmed shutdown:

```go
close(ingestionChannel)
```

### 4. Drain & Process

The worker pool consumers automatically drain and process any remaining events still buffered in the channel.

Use:

```go
sync.WaitGroup
```

to wait for all workers to complete.

### 5. State Snapshot

Before the application terminates, serialize and persist the latest state.

#### Dashboard State

```text
/state/dashboard.json
```

#### Deduplication State

```text
/dedup/window/<bucket>.json
```

### 6. Exit

Terminate the process gracefully with a clean exit.

## 6. What We Got Wrong (Design Iterations)

Building a high-throughput streaming system led to several architectural bottlenecks that required redesigns during development.

### A. Blocking ML Pipeline Creating System-Wide Backpressure

#### Initial Design

When building the Server-Sent Events (SSE) broker, we initially created unbuffered channels for new client connections:

messageChan := make(chan []byte)

The assumption was that the HTTP Flusher would immediately consume the data and send it over the network.

#### What Went Wrong

The ML Worker performs:

* Mathematical computations
* MinIO storage operations
* Anomaly persistence
* Forecast generation

During traffic spikes, the ML Worker became a bottleneck.

Since the send operation was blocking, the goroutine responsible for clean data processing stalled. This stall propagated backward through the pipeline and eventually prevented the SSE Broker from receiving data, effectively freezing the live dashboard.

#### The Fix

We introduced a non-blocking dispatch mechanism using a `select` statement.

If the ML pipeline is overloaded, specific metrics are skipped instead of blocking the entire system.

This ensures:

* Live Event Feed remains responsive.
* SSE delivery remains real-time.
* Storage and ingestion continue uninterrupted.

---

### B. The 1-Event-to-1-Metric Assumption (The Riverbed Case)

#### Initial Design

The ML pipeline assumed that every incoming event contained exactly one numerical metric.

Examples:

* `cpu_usage_percent` (Dynatrace)
* `http_request_rate` (Prometheus)

#### What Went Wrong

While integrating Riverbed mock data, we discovered that a single Riverbed event contains multiple metrics simultaneously:

* `rtt_ms`
* `throughput_mbps`
* `packet_loss_percent`

The original ML worker could extract only one metric per event, leaving critical network telemetry unanalyzed.

#### The Fix

We redesigned the extraction phase to support a **1-to-Many** extraction model.

The worker now:

1. Extracts all relevant metrics from a payload.
2. Maps each metric into an independent processing flow.
3. Executes Z-Score anomaly detection per metric.
4. Runs forecasting models concurrently.

This ensures complete observability and analysis coverage for multi-metric events such as Riverbed telemetry.
